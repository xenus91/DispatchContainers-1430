# MAX Dispatch — Design

Панель диспетчеризации контейнерных перевозок + бот в мессенджере MAX для водителей.
Платформа: **только веб** (`packages/web`) — та же React-сборка открывается в браузере на ПК и
встраивается как MAX Mini App. Визуальное направление: плотный «центр управления» (ops console) —
тёмная поверхность, высокая контрастность, данные важнее украшений, тревоги видно с трёх метров.

CSS-переменные в `packages/web/src/web/styles.css` (тёмная тема по умолчанию, без переключателя —
диспетчер сидит в панели весь день).

Никаких фиолетовых градиентов, никаких «карточек с большими радиусами» — радиус 6–8px максимум.

## Typography

- Display + UI: **Manrope** (600/700 для заголовков, 500 для интерфейса).
- Данные (номера контейнеров, координаты, телефоны, время): **IBM Plex Mono** — моноширинный,
  чтобы TCNU8793586 и 55.329167, 37.456876 читались без ошибок.
- Подключение — Google Fonts через `@import` в `styles.css`; размеры: 12/13/14/16/20/28,
  line-height 1.45 для текста, 1.15 для заголовков.

## Pages & Screens

- **Вход** (`pages/login.tsx`) — телефон → OTP-код из бота MAX. Две ступени на одном экране.
- **Заявки** (`pages/requests.tsx`, `/`) — основной экран: лента тревог сверху, таблица активных
  заявок (номер, контейнер, водитель, статус, время выгрузки, последнее обновление), фильтры по
  статусу, кнопка «Новая заявка».
- **Карточка заявки** (`pages/request-detail.tsx`, `/requests/:id`) — все 15 полей «Договор-заявки»,
  назначение/переназначение водителя, отмена, история статусов, вложения от водителя, комментарии.
- **Новая/редактирование заявки** (`pages/request-form.tsx`, `/requests/new`, `/requests/:id/edit`).
- **Сотрудники** (`pages/staff.tsx`, только для роли admin) — карточки водителей/диспетчеров,
  генерация invite-ссылок с выбором срока (1 ч / 24 ч / 72 ч / 7 дней), блокировка, журнал
  попыток доступа.
- **Настройки** (`pages/settings.tsx`, только admin) — интервал автонапоминания по умолчанию,
  состояние бота MAX (токен задан / режим заглушки), адрес вебхука.

## Key User Flows

1. **Вход:** телефон → сервер проверяет, что сотрудник активирован → бот отправляет OTP в личный
   чат MAX → ввод кода → сессия (Bearer-токен в localStorage, работает и внутри iframe MAX).
2. **Заявка:** диспетчер создаёт заявку → назначает водителя → бот присылает водителю карточку с
   кнопками статусов → водитель жмёт статусы, прикладывает фото/комментарий → диспетчер видит
   обновления в таблице и получает уведомление в MAX.
3. **Тревога:** водитель жмёт «Возможно опоздание»/«Срыв заявки» → выделенное уведомление
   диспетчеру в MAX + запись в ленте тревог, пока её не подтвердят.
4. **Регистрация:** admin создаёт карточку сотрудника → invite-ссылка с выбранным TTL → сотрудник
   жмёт «Начать» в боте → подтверждает телефон кнопкой «Поделиться контактом» → сверка с карточкой
   → активация.
5. **Напоминание:** планировщик каждую минуту сверяет время выгрузки и присылает водителю
   напоминание за настраиваемый интервал (глобальный дефолт + переопределение на заявке).

## Architecture

- **API**: oRPC-процедуры в `packages/web/src/api/routes/` (`auth`, `staff`, `requests`,
  `settings`), плюс plain-роут `POST /api/webhooks/max` для событий бота.
- **MAX-адаптер**: `packages/web/src/api/max/` — тонкий клиент Bot API (сообщения, клавиатуры,
  вложения). Без `MAX_BOT_TOKEN` работает в **режиме заглушки**: исходящие сообщения пишутся в лог
  и в таблицу `bot_outbox`, OTP-код виден в панели — это позволяет вести разработку и тесты до
  получения токена от заказчика.
- **Авторизация — своя, не Better Auth**: канал доставки кода — бот MAX, роли жёстко привязаны к
  карточке сотрудника и invite-потоку, поэтому проще и надёжнее собственные таблицы
  `sessions`/`otp_codes`, чем подгонять Better Auth под несуществующий у него транспорт.
- **State/sync**: TanStack Query, хуки в `src/web/queries/` (один файл на фичу), поллинг активных
  заявок и тревог раз в 10 секунд (вместо WebSocket — нагрузка мизерная, 2 диспетчера).
